# Runtime ensurepip overlay

The pinned Python 3.12.16 base contains `pip-25.0.1-py3-none-any.whl` inside
`ensurepip`. Installing pip26.3 into the active environment does not replace
that dormant wheel: R7's isolated fresh-venv probe installed25.0.1 while active
pip was26.3. This path is outside the active-distribution inventory. The package
audit found12 advisory occurrences/six unique IDs in25.0.1; that observation
does not establish an exploit in PamOlive or exhaustive scanner coverage.

The runtime now applies a local, strictly byte-pinned overlay before the existing
offline pip installation. It changes only `_PIP_VERSION = "25.0.1"` to
`_PIP_VERSION = "26.3"` in `ensurepip/__init__.py`, adds the already reviewed
`pip-26.3-py3-none-any.whl` under its correct name, and removes only the exact
verified old wheel. This is **PamOlive's local overlay**, not an assertion that
the upstream CPython3.12.16 source itself contains pip26.3.

The source pin was cross-checked with [CPython v3.12.16](https://github.com/python/cpython/blob/v3.12.16/Lib/ensurepip/__init__.py),
and the old wheel with the [PyPI25.0.1 release metadata](https://pypi.org/pypi/pip/25.0.1/json).
The new wheel is the same input already pinned by `requirements-bootstrap.lock`
and the32-file Linux Python manifest; this adds no network source or package.
Its METADATA bytes are separately pinned to
`ad63a8564cd158c8de9e6a912e92776b4abc56cfa2d8286ef4c35bfb9cb9e439`.

`deploy/ensurepip_bundle.py` is stdlib only. It never imports or executes the
wheel or ensurepip source while patching. It requires exactly five children:
the original three source files, `_bundled`, and the inherited empty
`__pycache__` directory. It requires the exact old-wheel singleton, no bytecode or unknown file,
regular non-hardlinked files and nonaliased parent directories. The unchanged
entry points are also pinned before writing: `__main__.py` SHA256
`ee735f518d0fc4dfec81f7aa3da1e052372ed4202c0da4eddd2587840beaecd7`,
`_uninstall.py` SHA256
`3a6e95d01c45e2e47c05df3c81073b895c97c1eb0e5b90ab175d6d9263fc81f2`.

The first R8 attempt at9e5afd2 stopped at `ensurepip_file_set`: the earlier
file-only offline inventory had omitted the base's **empty directory**.
Complete TAR-member inspection of the exact R7 archive established that it is
a real `__pycache__` directory with mode0755. The corrected guard retains this
directory and checks its nonaliased directory type, exact mode0755 and emptiness
both before any write and after replacement. A missing directory, file, symlink,
different mode, any child (including a zero-byte file or nested directory), or
another extra directory is refused. No cache directory or bytecode is deleted.
All source/API/sysconfig/wheel hashes and the deterministic patched bytes remain
unchanged. The failed first build remains diagnostic history; it produced no R8
image and is not retroactively called successful.

The actual target interpreter's `sysconfig` value `WHEEL_PKG_DIR` must be exactly
an empty string (`type(value) is str and value == ""`). Offline reading of R7's
`_sysconfigdata__linux_x86_64-linux-gnu.py` established that target fact; its bytes
are additionally pinned to SHA256
`ff048f75a99504e073c8a9b7e9da146763fcde6960d2291c19ca2b72cde9eb69`
and never modified or executed by the overlay. The earlier strict-None assumption
would have rejected the actual reviewed base and was corrected before build.
`None`, false booleans, zero, other types and external provider paths are refused;
this is not a general falsey-value admission. The
CLI requires Linux CPython3.12.16 as root and operates on the fixed stdlib path.
It checks the replacement filename, full byte size/SHA and bounded ZIP metadata
before any write. Module after-bytes must match the deterministic pin. A second
invocation refuses the changed state; it does not silently repair mixed states.

The Dockerfile copies the helper into the **runtime stage only**, and executes
it with `python -B` in `RUN --network=none`. Existing pip locks, no-index/hash
flags and directory-builder stay unchanged. No SDK or C wheel rebuild is caused
by an earlier-stage COPY of this helper. No ensurepip bytecode is generated by
the patch. Existing upstream bootstrap/venv API code, pip's ENSUREPIP_OPTIONS
handling, `altinstall`, `default_pip`, and the two entry-point files are preserved;
this is not a replacement stub that disables venv.

Public output is `/usr/share/pamolive/python-materials/ensurepip-bundle.json`.
It records before/after pins, unchanged entry-point hashes and the correctly
named old/new wheel identities. `recipe_base_reference` describes the expected
recipe input, not an independently verified OCI identity inside the container.
`build_verified` and `attestation_verified` remain false. The wider trusted
recipe/context, base digest, exact archive and qualification pipeline must bind
the result later. File verification assumes the reviewed build runner; it is
not a filesystem transaction resistant to a malicious root process racing every
operation. A filesystem error after writes aborts the Docker RUN and produces
no success proof or accepted layer; there is no silent partial success.

Removing the old wheel from the final merged filesystem does **not** erase its
bytes from the pinned base's historical OCI layers, nor update the dormant
bundle in intermediate builder images. Those layers remain part of the image's
history and must be reported honestly. This change fixes the supported runtime
bootstrap path and does not claim an image containing zero historical25.0.1
bytes, a clean vulnerability verdict, or a High exception.

Local verification, without Docker, PG, downloads, or imported application code:

```powershell
.\.venv\Scripts\python.exe -B -m unittest tests.test_ensurepip_bundle tests.test_python_materials
.\.venv\Scripts\python.exe -m ruff check deploy/ensurepip_bundle.py tests/test_ensurepip_bundle.py
.\.venv\Scripts\python.exe -m ruff format --check deploy/ensurepip_bundle.py tests/test_ensurepip_bundle.py
```

Unit fixtures use synthetic bytes with locally patched test-only pins; the CLI
has no mechanism to accept alternate pins. Independent review recrosses the real
source/wheel constants. The future exact runtime build still requires both
fresh-venv checks under read-only rootfs, no network, no capabilities and bounded
temporary storage: normal `venv` with pip, and `venv --without-pip` followed by
that venv's `python -m ensurepip`. Both must yield26.3 and pass `pip check`.
These real build/venv qualifications are not claimed by the pure unit suite.

# B3 — backport Kerberos sur le packaging Debian

État : **trois constructions complètes B3 échouées ; aucune image produit B3 qualifiée**. Le troisième essai a terminé les deux constructions/tests Debian et les douze cas ASN.1, puis échoué dans une validation de nom du vérificateur. Une intégration diagnostique distincte a ensuite validé les quatre bibliothèques réellement installées et leur ABI avec le vérificateur corrigé. Une nouvelle construction produit reste à exécuter. Les résultats B2 ne valident pas ces nouveaux paquets. La décision et les variantes rejetées figurent dans [ADR-019](adr-019-native-runtime-dependencies.md). Aucun NAS, KDC réel ou compte réel n'intervient.

## Delta et origine

La base reste MIT Kerberos `1.21.3-5+deb13u1` de Debian trixie-security. Le [commit MIT2058326](https://github.com/krb5/krb5/commit/205832663330da308d9d031a17326b68a16715fd) remplace la réallocation répétée du tableau ASN.1 par un comptage préalable et une allocation unique. Le [suivi Debian de CVE-2026-119079](https://security-tracker.debian.org/tracker/CVE-2026-119079) justifie la correction ciblée. Le patch conservé dans `deploy/krb5-asn1-sequence.patch` a pour SHA256 `e676f3727b3c984aa5a7baaafdb39394c8774c913ace0c3ce302e9b81aaa19ee`.

Les paquets portent la révision locale honnête `1.21.3-5+deb13u1+pamolive1`. Ils ne prétendent pas devenir la version amont1.22.3. Aucun dépôt sid, superposition de bibliothèques dans `/opt`, changement NLA, suppression Kerberos ou exception TLS n'est ajouté.

## Intégration du helper

`deploy/build-krb5.sh` est réservé à un stage de construction Linux amd64. Il possède deux phases pour permettre une coupure réseau vérifiable dans le Dockerfile :

1. `sh /build-fixtures/build-krb5.sh fetch` : récupérer les sources officielles, vérifier les preuves, installer les dépendances de construction. Exige `curl`, `gpgv`, le keyring Debian, Python, `dpkg-dev`, `devscripts`, `quilt` et les paquets de construction. Le `deb-src` créé reste dans ce stage jetable ; il ne modifie ni l'hôte ni le runtime.
2. Capturer le baseline des quatre bibliothèques stock avec l'outil indépendant `deploy/krb5_inventory.py --capture-baseline --output /usr/share/pamolive/krb5-backport/baseline.json`. Les quatre versions doivent être exactement celles attendues.
3. `RUN --network=none sh /build-fixtures/build-krb5.sh build` : compiler et tester la source Debian d'origine par `debian/rules build-arch`, exécuter le décodeur d'origine, appliquer le patch sans fuzz ni offset, compiler les paquets corrigés avec les tests Debian activés et rejouer le décodeur corrigé. Les dépendances sont installées avec `--arch-only` et la construction utilise `-B` : les documents PDF indépendants de l'architecture ne sont pas construits. Aucun `nocheck`, `-d` ou parallélisme des tests n'est permis.
4. Installer les quatre paquets de `/packages/runtime` dans le runtime. Dans les stages SDK, installer aussi les paquets de `/packages/sdk` : les dépendances exactes de `libkrb5-dev` et `krb5-multidev` doivent partager la révision locale pour éviter un mélange ou un retour au paquet stock.
5. Copier les preuves, puis capturer et vérifier l'inventaire indépendant contre les vrais fichiers installés, les SONAME et exports versionnés. Après création, rendre également le nouveau `inventory.json` lisible par l'UID runtime (`0444`) : le helper ne peut modifier les permissions d'un fichier créé ultérieurement. La comparaison ABI doit porter sur les octets ELF, sans se limiter à une déclaration dans un JSON.

Le helper attend dans `/build-fixtures` le patch exact, `check_krb5_asn1.sh` et `krb5_asn1_regression.c`. Les sources et objets avant/après restent séparés sous `/build/krb5-baseline/{src,build}` et `/build/krb5-patched/{src,build}`. La compilation d'origine est un témoin de comparaison ; les paquets livrables viennent exclusivement du second arbre. Une seule CPU et au plus1Gio restent les limites de construction locales ; leur respect appartient au contrôleur Docker.

Le sixième fichier de fixture est `krb5-test-keyring-seccomp.patch`, décrit ci-dessous. Les dépendances `python3-kdcproxy` et `python3-pyrad` sont celles du Python Debian : `PYTHON=/usr/bin/python3` est donc fourni au configure et aux tests MIT après vérification des imports. Les programmes de preuve restent exécutés par Python3.12 de l'image, et l'interpréteur applicatif ne change pas.

## Échec initial et compatibilité du harnais

Le premier essai local a effectivement validé la signature APT, la chaîne de checksums et le baseline des quatre ELF stock. Il a ensuite échoué dans `t_cccol.py` avant les tests ASN.1 dédiés et avant l'application du correctif CVE. La construction reste enregistrée `FAILED`.

Le patch Debian existant0012 détecte le refus ENOSYS de `keyctl add`, mais ne traite pas EPERM. Son chemin d'erreur concatène ensuite une chaîne et des octets, ce qui produit un `TypeError`. Un target de diagnostic privé, distinct du produit, a conservé le journal et l'échec2. Un probe dans le même stage avec réseau coupé a confirmé le retour1 et les octets `add_key: Operation not permitted\n`. Le premier target de diagnostic ne reproduisait pas tous les exports du helper ; il constitue un indice conservé, complété par ce probe précis. Aucun OOM, problème DNS ou problème de permission de volume n'est déduit de ce résultat.

La compatibilité TEST ONLY a pour SHA256 `1227fc24b76e62371bd94346e1a653906e2e964d39ac25f095c32ccbe8a9cd27`. Elle étend la détection à deux messages exacts ENOSYS/EPERM avec le seul retour1 et corrige le message d'erreur texte/octets. EACCES, les autres codes et les autres messages restent des échecs. Le patch est appliqué aux deux arbres avant leur compilation ; seul l'arbre corrigé reçoit ensuite le patch CVE MIT. Il ne modifie ni le décodeur, ni le runtime, ni seccomp, ni les capacités ou politiques PAM.

Le probe de réception ne valide que le profil EPERM effectivement observé : source Python et JSON sont conservés et hashés, le filtre seccomp doit être actif et l'interface réseau limitée au loopback. Une autre réponse oblige à requalifier le profil. Aucune capacité noyau n'est ajoutée pour rendre le test vert.

Le résultat Debian futur doit être `passed_with_capability_skips`, accompagné des occurrences réellement lues dans les journaux distincts baseline/patched pour `keyring collection tests` et `keyring ccache tests`. Le compteur est leur somme sur les deux phases. Le message historique « keyring support not built » reste celui du harnais Debian ; la preuve séparée établit ici une capacité noyau refusée dans le bac à sable, et non une désactivation de la compilation Kerberos. **Les parcours KEYRING ne sont pas qualifiés par ce profil.** Tous les autres tests restent activés et leurs échecs restent bloquants ; les éventuelles autres exclusions amont doivent être examinées et signalées.

Le deuxième essai complet a passé les tests Debian baseline, puis a échoué à la compilation du harnais ASN.1. Le diagnostic borné identifie six avertissements de paramètres volontairement inutilisés dans les en-têtes MIT `k5-thread.h`, promus par le `-Wextra -Werror` du harnais. Les racines des en-têtes tiers sont désormais déclarées avec `-isystem` ; ces options restent actives pour le code du harnais. Aucune option de compilation du produit n'a été changée pour contourner cet échec.

Deux diagnostics locaux distincts ont ensuite compilé et exécuté les six cas avant et les six cas après correction sur les vrais objets MIT. La copie corrigée reçoit le patch exact sans fuzz ; les hashes du décodeur sont respectivement `c35b90cfb1b765a112b091843aebb774d1c45b5f966ee99edfdfdd4bd2d6a0bc` et `218616414321edb52a00f8bb2659429bf9f820d3353978b705292088bf914740`. Les réallocations passent de256 à zéro, les allocations calloc de1 à2 et les points d'échec injectés de257 à2 ; aucun des douze cas ne laisse d'allocation suivie vivante. L'agrégat satisfait aussi le validateur indépendant. Ces diagnostics réutilisent les objets d'un ancien stage dont les tests Debian avaient échoué : ils **ne qualifient ni des paquets, ni le runtime, ni une nouvelle réussite de makecheck**.

Le journal partiel du deuxième essai expose aussi `LDAP KDB tests: slapd not found` et `sn2princ tests: cannot forward resolve ptr-mismatch.kerberos.org`, en plus des deux messages KEYRING. Aucun serveur LDAP système ni DNS externe n'est ajouté pour les rendre verts. La réception finale doit inventorier toutes les exclusions des deux journaux complets et distinguer ces limites amont des compteurs KEYRING contractuels.

Le troisième essai a terminé le build baseline avec six cas ASN.1 à410,4s, puis le build des paquets corrigés avec six cas ASN.1 à852,0s. Les deux journaux complets contiennent exactement les quatre exclusions ci-dessus, une occurrence chacune par phase : quatre occurrences KEYRING au total et quatre autres exclusions amont. Les quatre paquets runtime et six SDK ont été exportés avec les vingt preuves, dont les liens SHA, la chaîne APT et les compteurs ont été vérifiés sur leurs vrais octets. Ce résultat ne signifie pas que tous les tests optionnels amont ont été exécutés.

L'échec suivant concernait le nom authentifié du `.dsc`, `krb5_1.21.3-5+deb13u1.dsc` : le vérificateur refusait le caractère `+`. La correction conserve les bornes et l'interdiction des séparateurs, parcours et caractères non ASCII. Un probe d'intégration séparé a réutilisé les vrais paquets installés et les preuves de ce troisième essai, avec le nouveau vérificateur copié après les layers de compilation conservés. `--capture` puis `--verify` ont réussi sous réseau coupé ; les quatre ELF exportés correspondent à leurs hashes. Les SONAME et exports versionnés sont identiques au baseline :171 pour GSS-API,107 pour k5crypto,657 pour krb5 et101 pour krb5support. Le manifeste diagnostique a pour SHA256 `315c8319ef8744852632ba90dde40e0ac07921a175af80dd3eda91383d0fc90e`. Il atteste la cohérence de ces quatre bibliothèques, pas une réception NLA, PostgreSQL/TLS ou produit, ni une preuve cryptographique autonome de compilation.

## Chaîne de provenance

Le helper vérifie réellement l'[InRelease trixie-security](https://security.debian.org/debian-security/dists/trixie-security/InRelease) par `gpgv` et le keyring Debian installé. Ce contrôle est distinct du moteur de vérification utilisé par APT, qui peut être `sqv`. Il conserve le statut réel `VALIDSIG`, le fichier signé, son contenu extrait et le keyring employé. Il refuse les statuts de signature invalides et un Release expiré ou futur.

Le SHA256 et la taille de `main/source/Sources.xz` sont lus dans le Release authentifié. Le paragraphe exact `krb5` et sa version attendue lient ensuite les octets du `.dsc`, de l'archive amont et de l'archive Debian. Les deux archives possèdent en plus des SHA256 épinglés dans le helper. La décompression et les fichiers de preuve sont bornés. Une mise à jour du dépôt qui supprime la version attendue provoque un refus ; elle ne sélectionne pas automatiquement une nouvelle version.

La signature personnelle de l'uploader du `.dsc` n'est pas revendiquée : l'authentification des octets du `.dsc` provient ici de la chaîne APT signée. Le `.dsc` et ses checksums demeurent contrôlés. Les fichiers `.changes` et `.buildinfo` ainsi que le journal de construction d'origine sont conservés séparément dans `/packages/build-records`. Ils ne sont pas copiés avec un KDC, un compilateur ou des keytabs dans l'image d'exécution.

`/usr/share/pamolive/krb5-backport/` conserve la chaîne signée, les deux patches distincts, le baseline ELF, les deux résultats du harnais, son code C et son wrapper, l'agrégat ASN.1, le résultat des tests Debian et les deux journaux baseline/patched, ainsi que le code et le résultat du probe KEYRING. Les vingt fichiers de preuve sont bornés à32Mio chacun et128Mio au total. Le manifeste de provenance relie leurs SHA256. Le vérificateur stdlib contrôle les liens entre ces octets, les paquets et l'ABI ; la vérification cryptographique PGP est effectuée au build. Ces métadonnées ne constituent pas une preuve cryptographique autonome de compilation. L'attestation CI de l'archive exacte et la revue indépendante restent nécessaires. Les journaux doivent être examinés avant toute publication, y compris pour les identifiants et secrets synthétiques créés par les tests MIT.

## Portes de réception restantes

- Régression ASN.1 sur les vrais objets MIT : liste vide et longue, mauvais tag, troncature, chaque échec d'allocation et nettoyage partiel. Les wrappers doivent démontrer256 réallocations avant et zéro après, avec leurs nombres d'allocations attendus ; un wrapper inopérant doit échouer.
- Succès effectif des tests Debian/MIT, sans réseau externe, et lecture des résultats. Les tests ciblés ne remplacent pas `make check`.
- Installation et cohérence des quatre paquets runtime : `libkrb5-3`, `libk5crypto3`, `libkrb5support0`, `libgssapi-krb5-2`. Comparaison des SONAME et symboles versionnés avant/après, hashes ELF et résolution dynamique réelle des consommateurs FreeRDP/Guacamole/libpq.
- Requalification NLA et SSH/RDP, gardes de destination P0, contrôles des pins avant secrets, refus des redirections, révocations et captures. PostgreSQL TLS/SCRAM, transactions, concurrence et restauration doivent être rejoués sur B3.
- Rescan de l'archive B3 exacte et SBOM incluant les paquets locaux, les sources et le correctif. Un finding fondé sur la version amont doit rester visible. Une éventuelle décision `fixed_by_backport` s'appuie sur les preuves de ce correctif précis ; elle ne devient pas une exemption globale Kerberos.

Ces portes ne sont pas marquées réussies par l'ajout du helper. Le comportement de Kerberos réel avec des annuaires, DNS ou KDC d'entreprise, la compatibilité d'autres architectures CPU et la réception Synology restent hors de cette préparation N0.

Contrôles de préparation exécutés : syntaxe shell et deux programmes Python embarqués valides ; neuf cas de parsing de métadonnées synthétiques réussis (normal, index altéré, pin source altéré, Release expiré/futur, signature absente/invalide, version inattendue, champ dupliqué). Ces essais ne vérifient pas une signature PGP réelle et ne remplacent pas le build. La contre-revue Red Team est favorable au périmètre, avec vérification du répertoire `build/` dans les règles Debian exactes et rappel des permissions du manifeste créé ultérieurement. Le fichier `debian/rules` de l'archive épinglée confirme `--sourcedir=src --builddir=build` et `dh_auto_test --no-parallel`.

Après l'échec initial : syntaxe shell et trois programmes Python embarqués valides ; cinq cas purs de compatibilité KEYRING réussis (deux refus de capacité reconnus, EACCES/code2/autre erreur toujours bloquants) ; deux tests shell confirment la conservation du code d'échec et du journal par `run_logged`. Ces contrôles ne transforment pas l'échec initial en réussite B3.

# P1-F — Contre-revue du profil d’exécution de 22 risques OS

Revue indépendante du 12 novembre 2026. **Aucune exception CI activée, aucune qualification de production, aucun usage de comptes privilégiés réels.** Le périmètre est le développement N0 synthétique. Les 22 cas restent présents dans les résultats bruts ; une restriction de parcours ne corrige pas la bibliothèque vulnérable.

Cette revue couvre les **17 cas dépendant du profil** et les **5 propositions cJSON/Expat dont le code est présent**, issus de `p1-f-os-high-triage.md` et `p1-f-os-reviewed-build-findings.md`. Elle ne rouvre ni les deux décisions GCC, ni les neuf composants physiquement absents, ni le backport ASN.1 B3. La preuve publique correspondante est [p1-f-os-runtime-profile.v1.json](../.github/qualification/evidence/p1-f-os-runtime-profile.v1.json) : 22 CVE uniques, préconditions, limites, hashes des fichiers relus et faits binaires sélectionnés. Ce JSON décrit une analyse ; ce n’est pas une politique/VEX signée.

## Conclusion et conditions avant une décision N0

Le parcours normal comporte des obstacles concrets à ces attaques : moteur sans secrets applicatifs, UID distinct, environnement neuf C.UTF-8, aucun affichage X, répertoire privé, paramètres de session imposés par le serveur et PostgreSQL obligatoire dans le superviseur. Cela soutient des **candidatures individuelles à une non-accessibilité conditionnelle** pour le laboratoire, après rattachement à l’image finale et contrôle du profil. Cela ne justifie aucune exemption globale par paquet.

Trois garanties manquent pour transformer le préflight actuel en preuve de ces conditions : commande effective du service web, montages tmpfs et environnement des rôles web/jobs. Cinq mutations ont été acceptées par appels Python purs à `synology_preflight.validate()` sur un plan synthétique valide : commande alternative, utilisateur alternatif, tmpfs inscriptible sur `/etc/fonts`, `LANGUAGE` avec locale non-C et `DISPLAY`. Aucun conteneur, fichier de configuration, compte ou réseau n’a été créé par cette reproduction. **Le Compose versionné ne contient pas ces mutations.** L’acteur nécessaire est un auteur de configuration de déploiement ; aucun chemin permettant à un locataire ordinaire de modifier cet environnement n’a été trouvé dans cette revue ciblée.

Recommandation minimale avant toute décision fondée sur le profil :

1. Fixer ou refuser explicitement les substitutions de commande/utilisateur du service applicatif ; contrôler aussi le CMD de l’image qualifiée. Maintenir le superviseur, sa vérification PostgreSQL et la séparation des UID.
2. Valider les destinations/options tmpfs par service, en plus des volumes déjà contrôlés. Refuser les ombrages de bibliothèques, configurations de police, binaire ou code applicatif. Vérifier les montages effectifs sur l’instance N0.
3. Fixer les locales de tous les processus enfants, retirer les variables de catalogues, d’affichage et de configuration de police non approuvées ; vérifier les noms/valeurs publiques nécessaires sans journaliser les secrets. Le moteur possède déjà un environnement réduit ; web/jobs héritent actuellement de `os.environ`.
4. Rejouer ces refus comme tests automatisés du préflight ; ajouter une sonde réelle non destructive des commandes, UID/capacités, `NoNewPrivs`, montages, variables approuvées et fichiers de police. Les tests runtime actuels contrôlent UID, capacités et séparation des secrets, mais pas l’ensemble de ces hypothèses.
5. Refaire le scan et la comparaison ciblée des consommateurs sur **l’archive finale B3**, puis décider CVE par CVE avec échéance et invalidation en cas de changement. Pour les fonctions cJSON et Expat présentes, compléter les sources Debian exactes et les chemins internes ciblés ; l’absence d’un import dynamique seule n’est pas une preuve suffisante.

Ces propositions ne sont pas implémentées par cette revue. Aucun seuil scanner, contrôle PAM, MFA ou frontière de provenance n’est changé.

## Identité et force des preuves

Le témoin binaire relu ici est **B2 Linux amd64**, archive SHA-256 `91f42cac5b0700f61129b9b136a4626efb1c95c13ee5df95e74c2d9c4c756091`, manifeste OCI `sha256:d0f194f8a34c33ae659c76acad6879414f83a9a7d86f93db672bac7522dbb3a8`, configuration `sha256:bb310bd26a512a93a5cecf7b9e55109a5551878969a1e6baf939080a325f008b`. Dix-neuf chemins réguliers ont été lus en mémoire dans les layers, sans extraction ni exécution ELF. Ce relevé sélectionné n’est pas une sentinelle de tout le système de fichiers.

Le graphe historique de **844 ELF** appartient au témoin GDI `bf5d0075a25d2fc834aa5b21690fac709c62244a5f3330eee8296e1f58512cca`. Il conserve notamment une ancienne copie Kerberos embarquée par psycopg-binary. B2 utilise le driver C et les bibliothèques système : il serait incorrect d’attribuer les 844 ELF historiques à B2 ou B3. Les imports des dix-neuf chemins B2 sélectionnés ont été relus indépendamment ; les absences globales d’import citées ci-dessous restent celles du graphe historique.

Les sources FreeRDP 3.33.1 et Guacamole 1.6.0 ont été relues depuis leurs archives déjà vérifiées, respectivement SHA-256 `4431bbf04d370545cfe2924b9d9f116b95c90c64ff156b2550bbaf82d34e7124` et `8bc45675da96d7b6f39728160181e3d4ff3c08f460f6d26de5805b642bf13f2b`. Les sources et patches Debian exacts de Fontconfig/cJSON ne sont pas ajoutés à cette preuve. Leur absence reste une limite ciblée avant fermeture des appels internes.

Les hashes individuels des fichiers du checkout distinguent le code relu d’une image ancienne et d’un arbre local en cours de modification. Les nouveaux tests B3, même réussis, ne remplacent pas une qualification de l’application finale. Le correctif ASN.1 119079 ne corrige pas implicitement 107778.

## Contrôles effectivement présents

`deploy/runtime.py` exige une URL PostgreSQL et démarre web/jobs UID1000 et le moteur UID1001 sans groupes supplémentaires. Le moteur reçoit seulement PATH, LANG=C.UTF-8, les deux préfixes natifs approuvés et PYTHONUNBUFFERED. `native_runtime.py` crée HOME/GUACAMOLE_HOME en mode0700 et lance le guacd fixe sur loopback. Web/jobs héritent, eux, de l’environnement du superviseur.

Dans `platform_modules/pam/native.py`, le serveur fixe la police, le type de terminal et les paramètres RDP NLA/certificat ; les transferts, disques, SFTP, clipboard et arguments arbitraires sont restreints. Cela empêche de confondre un flux SSH de terminal avec une API d’upload de fichier Fontconfig. Le code Guacamole `src/terminal/display.c` appelle néanmoins Pango/Cairo : l’analyse de configuration de police existe réellement.

Le Compose Synology N0 livre une racine en lecture seule, aucun montage hôte applicatif ou X11, aucune capacité SYS_ADMIN, `no-new-privileges` et des réseaux applicatifs internes. `check_runtime.py` vérifie effectivement les UID, CapEff=0 et l’inaccessibilité des secrets applicatifs depuis le rôle natif. **Il ne vérifie pas actuellement la locale, DISPLAY/FONTCONFIG, les montages ou l’ensemble des chargeurs de plugins.** Le Compose générique n’a pas toutes les restrictions de la topologie N0 ; cette conclusion ne s’y étend pas automatiquement.

Les extensions admises sont signées et leurs wheels pures Python inspectées. Elles ne constituent pas un bac à sable : du code Python approuvé reste capable d’appeler des bibliothèques natives. Une nouvelle extension consommant SQLite, cJSON Utils, XML ou GSS doit invalider la décision concernée.

## Validation réalisée et limites

- Lecture de code/configuration, archives sources épinglées et dix-neuf chemins B2 ; aucun ELF chargé ou exécuté, aucune archive extraite sur le système de fichiers.
- Relecture des avis Debian individuels ; les références sont maintenues dans chaque ligne et dans le JSON. Les constats binaires sont liés aux hashes, pas déduits d’un nom de paquet.
- Reproduction pure Python des cinq acceptations du préflight. Ce sont des écarts vérifiés de validation de configuration, **pas cinq exploits runtime**.
- Aucune nouvelle suite PostgreSQL, concurrence, transport, charge, migration ou restauration exécutée dans cette mission documentaire. Les résultats historiques restent ceux de leurs propres rapports.
- Aucun accès NAS/réel, aucune donnée privée ou secret, aucun changement de politique/code/dépendance, aucun commit/push/déploiement par cette revue.

Les capacités KEYRING, LDAP KDB et DNS externe non exercées par les tests amont B3 restent des limites distinctes ; elles ne permettent ni de rejeter ni de valider par déduction les 22 parcours ci-dessus. Avant une éventuelle utilisation N0, il faut la preuve du profil effectif sur l’image finale, le scan brut de cette image et les décisions individuelles revues. L’usage privilégié réel et la production restent exclus de cette conclusion.
